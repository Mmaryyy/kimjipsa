# implement-feature

요구사항 ID 하나 또는 묶음을 구현한다. 문서 경로는 `docs/` 기준이다.

## 절차

1. **요구사항 확인**: `docs/01-project/REQUIREMENTS.md`에서 ID, 범위(MVP/M3/v1.1), 관련 요구사항을 찾는다. 범위가 M3·v1.1이면 사용자에게 지금 구현할지 확인한다.
2. **명세 원문 확인**: `docs/기능명세.html`에서 해당 요구사항 행, 확인 시나리오(`SCN-*`), 확정 정책, 프라이버시 규칙을 읽는다. 문서와 원문이 다르면 원문이 맞다.
3. **미결 확인**: `REQUIREMENTS.md`의 `[확인 필요]`나 `docs/04-planning/DECISIONS_REQUIRED.md`에 걸린 항목이면 **추측해서 구현하지 않고** 사용자에게 결정을 요청한다. 기획서 §12·명세의 "정해야 할 것"도 같다.
4. **구조 확인**: `docs/02-architecture/ARCHITECTURE.md`, 파일을 만들거나 옮기면 `docs/02-architecture/FSD.md`. 코드를 쓰기 전에 `docs/03-guidelines/CODING_STANDARDS.md`를 읽는다. API가 걸리면 `API_CONVENTIONS.md`, 상태는 `STATE_MANAGEMENT.md`.
5. **데이터 모델 확인**: `docs/02-architecture/DATA_MODEL.md`. 명세에 없는 필드는 추가하지 않고 사용자에게 올린다.
6. **범위 정의**: 이번에 만들 ID, 건드릴 슬라이스, 만들지 않을 것을 한두 문장으로 정리한다. 요구사항에 없는 기능을 끼워 넣지 않는다.
7. **기존 코드 탐색**: 같은 역할의 컴포넌트·함수가 있는지 `rg`로 먼저 찾아 재사용한다.
8. **구현**: 변경 범위를 최소로 한다. 권한 규칙(개인 일정 필터)은 entity 서버 함수 한 곳에 두고 화면과 챗봇이 함께 쓴다. 직접 요청과 챗봇 판단 변경은 구분한다.
9. **테스트 작성**: 테스트를 쓸 때는 `write-tests` 스킬을 따른다. **테스트·빌드·린트 실행은 사용자 승인 뒤에만 한다.**
10. **요구사항 충족 점검**: 해당 `SCN-*` 시나리오를 코드와 대조해 읽고 충족 여부를 직접 확인한다(실행이 필요하면 승인 요청).
11. **마무리**: 코드 작업을 마치면 `yarn format`을 돌리고 `yarn format:check`가 통과하는지 확인한다(`package.json`이 없으면 건너뛰고 이유를 보고). 마이그레이션·인증/권한·환경 변수·되돌리기 어려운 변경이 있었다면 끝내기 전에 "검증할까요?"를 한 줄 근거와 함께 제안한다.
12. **보고**: 구현한 요구사항 ID, 변경 파일, 검증 결과(실행한 것/못 한 것), 남은 확인 필요 사항. 문서·구현이 어긋나면 임의로 판단하지 말고 알린다.

## 금지

- 승인되지 않은 기술·구조 결정을 코드에 박지 않는다(PROPOSED/PENDING 항목).
- 요구사항에 없는 기능 추가, 불필요한 의존성 추가.
- 상태를 저장해서 파생 값(부족/임박/D-day)을 두지 않는다.

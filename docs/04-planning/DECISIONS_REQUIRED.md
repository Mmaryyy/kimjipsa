## DEC-001
### Topic
개인 일정의 제목·장소·메모를 배우자에게 보내지 않으면서 시간 칸은 보이게 하는 DB·실시간 구조.
### Background
CAL-04: 배우자의 개인 일정은 희미한 칸만 보이고 제목·장소·메모는 "브라우저에 전달되지 않아야" 한다(명세 프라이버시 규칙). 그런데 RLS는 행 단위 접근 제어라 한 행의 일부 컬럼만 숨기지 못한다. 기획서 §09는 브라우저가 Supabase에 직접 연결하는 것을 로그인·실시간 구독으로 한정하므로, 일정 Realtime을 쓰면 개인 일정 페이로드가 유출될 수 있다.
### Options
A. 시간 정보 테이블(`events`)과 내용 테이블(`event_details`: title/place/memo)을 분리하고, 내용 테이블 RLS를 "공유이거나 작성자"로 제한. 일정 조회·구독은 시간 테이블만 직접.
B. 일정은 서버 라우트로만 조회하고 Realtime은 쓰지 않음(변경 시 폴링/푸시로 갱신). 장바구니만 Realtime.
C. 마스킹용 뷰(security_invoker)로 컬럼을 가리고 뷰를 조회. Realtime 구독 가능 여부와 RLS 동작을 검증해야 함.
### Recommendation
A. 행 분리는 DB 수준에서 유출을 막고, 챗봇·화면이 같은 서버 함수를 쓰는 규칙과도 잘 맞는다. 선택 후 canary 테스트(배우자 세션으로 직접 조회·구독)로 검증한다.
### Impact
일정 스키마와 `entities/event` 서버 함수 구조, 개인 일정 전환(CAL-03) 구현 방식, 첫 마이그레이션이 달라진다. 보안·개인정보 항목이라 승인 필수.
### Status
CONFIRMED (2026-10-16, 권장안 A, ADR-0012)

## DEC-003
### Topic
AI 키를 서버에서 암호화해 저장하는 방식.
### Background
ACC-08은 "서버에서 암호화 저장, 화면엔 끝자리만"만 규정한다. 방식과 마스터 키 관리가 없다. 이 키는 가정의 외부 서비스 비용과 직결된다.
### Options
A. 앱 레벨 AES-GCM, 마스터 키를 Vercel 환경 변수에 보관.
B. Supabase Vault(pgsodium) 사용.
C. 외부 KMS.
### Recommendation
MVP는 A 또는 B 중 단순한 쪽. 키 교체 절차(마스터 키 회전 시 재암호화)와 로그 마스킹 규칙을 함께 정한다. 사용자 승인 전 구현하지 않는다.
### Impact
ACC-08/09, 챗봇 서버 코드, 환경 변수·시크릿 구성(변경 시 검증 제안 필요).
### Status
CONFIRMED (2026-10-30, 권장안 A, ADR-0016). AI 키에 쓴다(구글 캘린더 연동은 범위 제외).

## DEC-004
### Topic
예약 작업을 어디서 어떻게 실행할지.
### Background
필요한 작업: 사용자별 시각의 아침 요약(CAL-10), 일정별 시작 N분 전 알림(CAL-11), 5분 무활동 후 대화 요약(BOT-12), 90일 지난 대화 삭제(BOT-14), 선제 제안(BOT-17, M3), 푸시 발송. 서버리스에서는 타이머가 없고, Vercel 무료 플랜의 Cron은 실행 빈도 제한이 있어 분 단위 알림이 어려울 수 있다(플랜 한도 확인 필요).
### Options
A. Supabase `pg_cron`(1분 주기) + 서버 라우트 호출 또는 Edge Function.
B. Vercel Cron(플랜 제약 확인) + 서버 라우트.
C. 외부 스케줄러 서비스.
### Recommendation
A가 후보. 확정 전에 실제 플랜 한도를 확인하고, 대화 요약은 "다음 대화 시작 시 이전 대화가 5분 이상 비었으면 요약" 같은 지연 처리를 허용할지도 함께 정한다.
### Impact
알림 요구사항 전체, DB 스키마(푸시 구독, 발송 기록), 비용.
### Status
CONFIRMED (2026-10-20, 권장안 A) → ADR-0013
### Decision
사용자 결정(2026-10-20): Supabase `pg_cron`(1분 주기)으로 예약 작업을 돌린다. 발송 대상 계산과 웹 푸시 발송은 서버 라우트가 맡고, `pg_cron`은 `pg_net`으로 그 라우트를 공유 시크릿 헤더와 함께 호출한다. 대화 요약(BOT-12)의 지연 처리 허용 여부는 P10에서 정한다.

## DEC-005
### Topic
같은 이메일의 카카오·구글 로그인을 별개 계정으로 유지하는 방법.
### Background
명세 확정 정책: 수단별 별개 계정, 합치기 없음. Supabase Auth는 기본적으로 같은 이메일 아이덴티티를 연결하는 동작이 있어 설정/우회 방식이 필요할 수 있다. 카카오는 이메일 제공 여부가 설정에 따라 다르다.
### Options
Supabase Auth의 자동 연결 설정 조정 / 이메일 대신 제공자 id로 구분 / 계정 연결을 허용(명세 변경).
### Recommendation
구현 전에 Supabase 동작을 확인한 뒤 명세와 맞는 방식을 고른다. 명세와 다르게 동작하면 사용자에게 보고하고 문서를 먼저 고친다.
### Impact
ACC-01, 보안(계정 탈취 가능성), 온보딩 흐름.
### Status
CONFIRMED (ADR-0009)
### Decision
사용자 결정(2026-10-15, 권장안): 카카오 동의 항목에서 이메일을 받지 않고, 계정은 제공자 + 제공자 사용자 id로 구분한다. 이메일은 식별·연결에 쓰지 않는다. Supabase 동작(카카오 이메일 없이 로그인되는지, 같은 이메일의 구글과 합쳐지지 않는지)은 P2 초반에 시험해 확인하고, 다르게 동작하면 구현을 멈추고 보고한 뒤 문서를 먼저 고친다.

P10(ACC-15) 메모: `invites.created_by`·`accepted_by`의 사용자 삭제 시 FK 처리(`ON DELETE SET NULL` 여부, null 허용 및 사용 여부 판정 포함)는 ④ 탈퇴자 작성자 표시와 함께 결정한다. P2에서는 삭제 규칙을 바꾸지 않는다.

## DEC-010
### Topic
판정 기준이 모호한 요구사항.
### Background
INV-16 "비슷한 이름", CART-12 "같은 이름" 판정(공백·대소문자·부분 일치?), CART-05 "최근 구매가 많은 순"의 기간. `CODING_STANDARDS.md` §5는 동일성 규칙을 한 곳에서 관리하라고만 한다.
### Options
정규화 후 완전 일치(공백·대소문자 무시) 우선, 유사 판정은 부분 포함 정도 / 최근 N일 지정.
### Recommendation
MVP는 정규화 후 완전 일치 + 포함 관계, 최근 구매는 최근 90일(예시, 사용자 확정 필요).
### Impact
재고·장바구니 등록 흐름.
### Status
CONFIRMED (2026-10-24, 권장안 승인)
### Decided so far
- 같은 이름(CART-12 포함): 앞뒤·중간 공백과 대소문자를 무시하고 정규화한 이름이 완전히 같으면 같은 이름이다.
- 비슷한 이름(INV-16): 정규화한 이름에서 한쪽이 다른 쪽을 포함하면 비슷한 이름이다(예: '우유' ↔ '서울우유'). 한 글자 차이 같은 편집 거리 판정은 쓰지 않는다.
- 최근 구매(CART-05): 최근 90일 동안 구매 완료한 횟수가 많은 순이다.
- 판정 규칙은 한 곳에서 관리한다(`CODING_STANDARDS.md` §5).

## DEC-013
### Topic
자체 도메인, 이용약관·개인정보처리방침, 에러 모니터링, DB 백업.
### Background
기획서 §11이 필요하다고 했으나 시기·도구·비용이 없다. 구글 로그인·캘린더 승인에는 소유 확인 가능한 도메인이 필요하다.
### Options
도메인 구입 시기(M1 로그인 심사 전 vs M3 전), 약관 작성 방식, 모니터링 도구, 백업 방식.
### Recommendation
로그인 심사 일정에 맞춰 도메인을 먼저 정하고, 약관은 최소안으로 베타 전에.
### Impact
외부 비용, 로그인 심사, 출시 일정. 비용이 발생하므로 승인 필수.
### Status
PENDING
### Decided so far
P2 범위(사용자 결정, 2026-10-15, 권장안): 개발은 Vercel 기본 도메인(`*.vercel.app`)과 localhost로 하고, 약관·개인정보처리방침은 "초안" 표시가 붙은 최소 문구로 동의 화면을 만든다(법률 검토를 거친 문서가 아니다). 정식 문서는 베타 전(P13)에 정한다.

P2 동의 기록(사용자 결정, 2026-10-16): `users.terms_accepted_at`, `privacy_accepted_at`(`timestamptz`), `terms_version`(`text`)을 최초 `complete_profile`에서 저장한다. 현재 초안 버전은 `draft-2026-10-16`이며, 표시 이름 수정 시 최초 동의 기록을 유지한다. 정식 약관 전환과 재동의 정책은 P13에서 정한다.
사용자가 "자체 도메인을 살 계획이 없다"고 했다. 구글 로그인(P2)은 기본 도메인과 테스트 모드로 가능하지만, 구글 캘린더 연동(CAL-15)은 2026-10-30에 범위에서 제외했다(아래 결정은 기록으로만 남긴다). 그래서 자체 도메인은 필요 없다. 모니터링 도구와 DB 백업은 미정이다.

[범위 제외로 무효] P9 구글 캘린더(사용자 결정, 2026-10-30): 자체 도메인 없이 `*.vercel.app` 으로 간다. 구글 앱 검증은 소유 확인한 도메인이 필요해 신청하지 않고, OAuth 동의 화면을 검증 없이 '운영(In production)' 상태로 둔다. 연결할 때 "확인되지 않은 앱" 경고가 뜨고, 민감한 범위에 동의하는 사용자는 프로젝트 전체 기간 100명까지다. 테스트 모드와 달리 7일마다 연결이 끊기지 않는다. 범위는 읽기와 쓰기 모두다(CAL-15). 사용자가 늘어 100명 한도가 문제가 되면 도메인 구입과 검증을 다시 정한다.

[범위 제외로 무효] P9 구글 캘린더 읽기·쓰기 범위(사용자 결정, 2026-10-30): 읽기는 연결할 때 사용자가 캘린더를 고르고, 캘린더마다 공유·개인을 정한다. 개인으로 정한 캘린더의 일정은 개인 일정 규칙(제목·장소·메모는 배우자에게 나가지 않음)을 따른다. 쓰기는 이 서비스의 공유 일정을 연결한 구성원 모두의 구글 캘린더에, 개인 일정은 작성자의 구글 캘린더에만 넣고 수정·삭제도 따라간다. 구글에서 읽어 온 일정은 다시 구글에 쓰지 않는다.

## DEC-014
### Topic
재고 카테고리에 아이콘을 붙이고 사용자가 바꿀 수 있게 할지, 방식은 무엇인지. 명세·`DATA_MODEL.md`에는 재고 카테고리 아이콘이 없다(새 요구사항).
### Background
사용자가 2026-10-15에 요청했다. 재고 카테고리(INV-07)는 이름만 있고 색은 없다(색은 일정 카테고리 CAL-08에만 있다). 가정마다 카테고리를 추가·편집할 수 있으므로 아이콘도 사용자가 정할 수 있어야 한다. 기본 카테고리 아이콘은 이미 의존성인 `lucide-react`에서 제공한다.
### Options
합의된 부분:
- 기본 카테고리 9개는 `lucide` 아이콘을 기본값으로 제공한다. 사용자가 입력한 문자(이모지 등)가 있으면 그것을 대신 표시한다. 기본 카테고리도 바꿀 수 있다.
- 아이콘이 없으면 카테고리 이름의 첫 글자 한 글자를 아이콘 자리에 표시한다(사용자 결정, 2026-10-15). 재고 카테고리에는 색이 없어 점 표시는 쓰지 않는다.
- 이모지 세트 등 새 라이브러리와 아이콘 선택기는 만들지 않는다. 입력은 기기 키보드의 이모지를 쓴다.
- 기본 카테고리 9개의 `lucide` 아이콘은 사용자가 후보 중에서 직접 골랐다(사용자 결정, 2026-10-15): 채소·과일 `carrot`, 정육·수산 `beef`, 유제품·계란 `milk`, 가공식품 `pizza`, 음료 `cup-soda`, 양념·소스 `flask-round`, 생활용품 `soap-dispenser-droplet`, 건강·뷰티 `heart-pulse`, 기타 `tag`. (추천안과 다른 것: 가공식품 `soup`→`pizza`, 양념·소스 `chef-hat`→`flask-round`, 생활용품 `spray-can`→`soap-dispenser-droplet`, 기타 `package`→`tag`)

제안(사용자 확인 전):
- 입력 허용 범위: 눈에 보이는 문자 한 글자(이모지 하나 또는 글자 하나). 서버에서도 같은 기준으로 검증한다.
- 저장 필드: `icon_kind`(`lucide` 또는 `text`)와 `icon_value`. 비어 있으면 아이콘 없음(화면에는 이름 첫 글자).
- 아이콘은 장식으로 처리하고(스크린리더 제외) 의미는 카테고리 이름이 전달한다.
### Recommendation
위 합의 + 제안대로. 입력 범위와 저장 방식은 확정 전까지 구현하지 않는다.
### Impact
`REQUIREMENTS.md` INV-07, `DATA_MODEL.md`(`inventory_categories`), `ROADMAP.md` P6, 가정 설정 화면(ACC-13). 기능명세·기획서 원본에는 아직 반영하지 않았다(사용자 요청 시 아티팩트와 복사본을 함께 고친다). 새 라이브러리가 없으므로 ADR은 필요 없다.
### Status
CONFIRMED (2026-10-24, 제안안 승인: 보이는 문자 한 글자, 서버 동일 검증, `icon_kind`·`icon_value`, 장식 처리)

## DEC-015
### Topic

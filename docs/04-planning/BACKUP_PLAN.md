# DB 백업 운영 절차

상태: 방식·주기·4주 보관은 CONFIRMED (DEC-013, 사용자 2026-11-11). 스크립트·launchd 템플릿 구현, 운영 등록·실제 백업·복구 확인은 미실행이다. 주 1회 백업을 4주 치 보관하며 스크립트 기본값과 launchd 설정은 4주다.

## 구현 범위

- 맥미니 launchd에서 주 1회 `scripts/backup-database.py`를 실행한다. 템플릿은 `scripts/com.kimjipsa.database-backup.plist`다. 실행 시각은 운영자가 조절할 수 있는 템플릿 값(일요일 03:00, 맥미니 시스템 시간대 기준)이다.
- `pg_dump --format=custom --no-owner --no-acl`로 public·auth·private 스키마와 데이터를 덤프한다. Supabase Storage 파일·pgmq 작업 큐·cron·Vault·프로젝트 설정은 이 백업에 포함하지 않는다.
- 개인 대화·첨부·AI 실행·확인·영수증 초안 및 관련 임시 상태는 데이터 덤프에서 제외한다. 이미 반영한 일정·재고·장바구니와 가족 기억은 포함한다. 복원 후 워커 등록은 다시 해야 한다.
- 목적지는 저장소 밖이어야 하며 폴더 700·덤프 600으로 제한한다. 접속 문자열·비밀번호는 인자로 넘기거나 로그에 남기지 않는다. 디스크 암호화·접근 권한은 운영자가 맥미니에서 확인한다.
- 중복 실행을 잠금으로 막는다. 임시 덤프 생성과 `pg_restore --list` 성공 후에만 정식 파일로 바꾸고 보관 기간이 지난 이 스크립트의 백업 파일을 지운다. 실패하면 기존 백업을 유지한다. 이 목록 검사는 실제 복구 검증을 대체하지 않는다.

## 운영자가 준비할 것

1. 주 1회 백업을 4주 치 보관한다. 개인정보 처리방침에도 같은 보관·파기 기간을 안내한다.
2. 맥미니에서 서버 버전 이상인 PostgreSQL 클라이언트의 `pg_dump`·`pg_restore`, Python 3를 준비한다. launchd는 셸 PATH를 읽지 않으므로 바이너리 폴더와 Python 경로는 절대 경로로 지정한다.
3. 저장소 밖의 운영 폴더에 스크립트 복사본, 인증 파일, 백업 폴더, 로그 폴더를 둔다. 백업·로그·인증을 Git이나 클라우드 동기화 폴더에 넣지 않는다.
4. libpq service 파일에 `[kimjipsa-backup]` 연결을 설정하고 비밀번호는 별도 passfile에 둔다. Session pooler(5432) 또는 직접 DB 연결을 사용한다. 호스트·사용자·DB·비밀번호는 Supabase의 실제 연결 정보를 운영자가 입력한다. 두 파일 모두 `chmod 600`으로 제한한다.
5. plist의 `__...__` 자리를 실제 절대 경로로 채우고 보관 주 수는 `4`를 유지한다. `PGSERVICE`, `PGSERVICEFILE`, `PGPASSFILE`, `KIMJIPSA_PG_BIN`, `KIMJIPSA_BACKUP_DIR`, `KIMJIPSA_BACKUP_RETENTION_WEEKS`는 이 작업에만 준다. 앱 `.env.local`이나 클라이언트로 전달하지 않는다.
6. 운영자가 수동으로 첫 백업을 실행하고 성공 로그·새 파일 시각·크기·권한을 확인한다. 다음 복구 연습도 통과한 뒤 LaunchAgents에 등록한다. 이번 구현 작업에서는 등록·원격 덤프를 실행하지 않았다.
7. 매주 백업 파일의 최근 수정 시각과 종료 코드를 확인한다. launchd 자체는 실패 알림을 보내지 않는다. 맥미니가 꺼져 있거나 로그아웃돼 있으면 LaunchAgent가 실행되지 않으며, 다음 로그인 후 담당자가 누락 여부를 확인한다.

## 복구 연습

1. 운영 DB와 분리된 로컬 Supabase를 준비한다. 운영 DB에 `pg_restore`를 실행하지 않는다.
2. `pg_restore --list <덤프>`로 목록을 확인하고, 테스트 DB의 기존 스키마와 충돌하지 않도록 복원 순서를 검토한다. Supabase 관리 auth 스키마는 버전·기존 객체에 맞게 선택 복원한다. `--clean`을 운영 DB에 실행하지 않는다.
3. 마이그레이션 버전과 맞는 스키마·auth 사용자/identity·public/private 데이터를 로컬에 복원한다. Supabase의 관리 역할·확장·소유권은 로컬 Supabase에서 준비한다. 덤프만으로 새 프로젝트가 자동 완성되지는 않는다.
4. 사용자·가정·멤버십·일정·재고·장바구니·가족 기억을 대조하고, 두 계정의 로그인과 가정 격리·개인 일정 마스킹을 확인한다. 대화·첨부·작업 큐는 복구되지 않아야 한다.
5. 운영 복구가 필요하면 담당자가 별도 승인 후 프로젝트 설정·Vault·cron·워커 등록·앱 환경 변수를 복원한다. 결과와 복원 시점을 기록한다. 지운 사용자나 데이터를 과거 백업에서 되살렸다면 삭제 요청을 다시 반영한다.

## 한계

주간 백업이므로 최악에는 최근 1주 데이터가 손실된다. 맥미니 한 곳에만 보관하므로 그 디스크 손실까지 대비하지 못한다. 두 번째 보관 위치·자동 실패 알림·Storage 파일 백업은 이번 범위에 추가하지 않았다. 실제 복구 성공이 확인되기 전에는 베타 필수 완료로 표시하지 않는다.

공식 기준: [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups). Free 플랜의 수동 외부 백업 권고와 Storage 파일 제외를 확인했다(2026-11-11).

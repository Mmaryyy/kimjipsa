# DB 백업 계획 (미구현)

상태: PENDING (DEC-013, 2026-10-30 사용자 결정 — 지금은 구현하지 않고 문서로만 남긴다)

## 왜 필요한가
일정·재고·장바구니는 Supabase Postgres 한 곳에만 있다. 잘못된 마이그레이션, 실수로 지운 데이터, 계정 문제가 생기면 지금은 되돌릴 방법이 없다. 베타를 넘어 다른 가정이 쓰기 전에는 정해야 한다.

## 선택지

| 방법 | 비용 | 해야 할 일 | 한계 |
| --- | --- | --- | --- |
| A. GitHub Actions 매일 `pg_dump` | 무료(Actions 사용량 안) | 워크플로 추가, `SUPABASE_DB_URL`(연결 문자열)·백업 암호화 키를 GitHub Secrets에 등록, 덤프를 암호화해 Actions 아티팩트로 30일 보관 | 아티팩트 보관 기간 제한, 복구는 수동 |
| B. Supabase Pro 업그레이드 | 월 약 $25(시작 전 최신 요금 확인) | 대시보드에서 플랜 변경 | 비용. 보관 기간은 플랜 기준 |
| C. 수동 덤프 | 무료 | 주 1회 직접 `pg_dump` | 잊으면 백업이 없다 |

권장안은 A다. 비용이 없고 CI(GitHub Actions)를 이미 쓴다. 결정할 때 Supabase 무료 플랜의 백업 제공 여부를 다시 확인한다.

## A안을 구현할 때 정할 것
- 덤프 범위: `public` 스키마 + `auth.users`(로그인 연결). `auth` 스키마 전체를 복원할지는 Supabase 문서로 확인
- 암호화: `age` 또는 `openssl`로 암호화한 뒤 업로드. 키는 GitHub Secrets와 비밀번호 관리자에 따로 보관
- 실행 시각: 매일 새벽(KST), 실패하면 GitHub 알림 메일
- 개인정보처리방침: 백업 보관 기간을 파기 항목에 적는다

## 복구 절차 초안
1. 새 Supabase 프로젝트(또는 같은 프로젝트의 빈 DB)를 준비한다.
2. 백업 파일을 내려받아 복호화한다.
3. `psql`로 스키마와 데이터를 복원한다(`supabase/migrations` 순서와 맞는지 확인).
4. 앱 환경 변수(Supabase URL·키)를 새 프로젝트로 바꾸고, 로그인·일정 조회로 확인한다.
5. 복구를 마치면 Vault 값(app_url 등)과 pg_cron 작업이 있는지 확인한다.

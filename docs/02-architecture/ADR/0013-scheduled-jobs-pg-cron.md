# 0013. 예약 작업: Supabase pg_cron + 서버 라우트

- 결정 ID: ADR-0013 (관련 DEC: DEC-004, CAL-09~11, ACC-11)
- 결정 날짜: 2026-10-20
- 상태: Accepted

## 배경
아침 요약(CAL-10), 일정 시작 N분 전 알림(CAL-11), 이후 대화 요약(BOT-12)·90일 삭제(BOT-14)는 정해진 시각에 돌아야 한다. 서버리스(Vercel)에는 타이머가 없고, Vercel 무료 플랜 Cron은 실행 빈도 제한이 있어 분 단위 알림이 어렵다. 사용자가 권장안 A를 승인했다(2026-10-20).

## 검토한 대안
- B. Vercel Cron: 무료 플랜 빈도 제한으로 분 단위 알림을 보장하지 못한다.
- C. 외부 스케줄러 서비스: 계정·시크릿 관리가 하나 더 늘어난다.

## 최종 결정
- Supabase `pg_cron`이 1분마다 실행되고 `pg_net`으로 서버 라우트(예: `/api/cron/notifications`)를 호출한다.
- 호출은 공유 시크릿 헤더로 인증한다. 시크릿은 서버 환경 변수와 Supabase(Vault 또는 cron 설정)에만 두고 코드·로그에 남기지 않는다.
- 발송 대상 계산(사용자별 아침 요약 시각, 일정별 `remind_before`, 개인 일정은 작성자에게만)과 웹 푸시 발송은 서버 라우트가 맡는다. 같은 알림을 두 번 보내지 않도록 발송 기록으로 중복을 막는다.
- 시각 계산은 `Asia/Seoul` 기준이다(ADR-0004).

## 결정 이유
추가 서비스 없이 분 단위 실행이 되고, 발송 로직은 다른 서버 코드와 같은 곳에서 테스트할 수 있다.

## 예상 영향
- Supabase 프로젝트에서 `pg_cron`·`pg_net` 확장을 켜야 한다(사용자 할 일).
- P5 마이그레이션: 푸시 구독, 앱 내 알림, 발송 기록, cron 등록.
- 로컬 개발에서는 cron 대신 라우트를 직접 호출해 확인한다.

## P5b 구현 (2026-10-21)

- `POST /api/cron/notifications`는 `x-cron-secret`과 `CRON_SECRET`을 상수 시간 비교하며, 누락·빈 값·불일치는 401이다. 쿠키 인증과 Origin 검사를 쓰는 일반 API와 분리한다.
- Vault `cron_secret`은 같은 값, `app_url`은 배포 앱의 HTTPS origin이다. 마이그레이션은 `kimjipsa-notifications` 작업을 `* * * * *`로 등록한다. 확장 활성화·Vault 값 등록·원격 적용·배포는 사용자 작업이다.
- 운영용 서비스 역할 키를 추가하지 않는다. `notification_worker` RPC는 Vault 시크릿을 매 호출 검사하고 snapshot·schedule·claim_push·release_push·delete_subscription 작업만 제공한다. 일반 세션으로 시크릿 없이 호출할 수 없다. 서버는 익명 클라이언트로 이 RPC만 호출한다.
- 서버가 DB 현재 시각을 받아 분 단위로 대상을 계산한다. 종일·시간 미정은 시작일 00:00 KST 기준이며, 개인 일정은 본인만 대상이다. D-day는 기존 `nextDday` 계산으로 다음 연간 날짜를 적용한다. 아침 요약은 사용자가 볼 수 있는 오늘 일정이 있을 때만 시각순 한 건으로 만든다. 시작 전 payload에는 일정 제목과 시작 시각을 담아 푸시·앱 내 목록에서 보여 준다(2026-10-22 사용자 결정). 개인 일정은 본인에게만 전송하며, 요약은 시각과 개수만 묶는다.
- 예약 로그 키는 시작 전 `reminder:<user>:<event>:<start instant>`, 아침 요약 `morning:<user>:<KST date>`다. 트랜잭션 잠금과 고유 키로 앱 내 알림과 기록을 함께 저장한다. 시점 변경으로 시작 시각이 같으면 같은 시작 전 알림을 다시 보내지 않는다.
- 푸시는 알림·구독 주소별 발송 로그를 네트워크 호출 전에 선점한다. 성공한 기기의 기록은 유지해 겹친 cron·요청 후 즉시 발송·재호출에도 중복 발송을 막는다. 404·410은 구독을 삭제하고, 그 밖의 오류·타임아웃은 실패한 주소의 선점만 풀어 다음 호출에서 5분 보충 창 안에 다시 시도한다(2026-10-22 사용자 결정, r114-f5). 선점 뒤 프로세스가 중단되거나 선점 해제가 실패하면 재시도하지 못할 수 있으며 앱 내 알림은 남는다. 5분 이내 새 알림을 배치당 20개 처리한다. 예약 계산은 `(DB 현재 시각 - 5분, DB 현재 시각]`을 보충하며 KST 자정을 넘는 경우도 포함한다. 같은 키는 다시 저장하지 않는다. 5분 이상 중단된 구간은 보충하지 않는다.
- P5a 일정 API는 DB 트랜잭션 성공 뒤 `after`로 푸시를 처리하고, cron도 남은 배우자 변경 알림을 처리한다. `push_enabled=false`이면 푸시만 건너뛴다. 404·410 구독은 지우고 오류 로그에는 상태 코드만 남긴다. 잠금 화면의 배우자 변경 안내는 일정 내용을 포함하지 않는다.
- VAPID 변수는 `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`(`mailto:`)다. `.env.example`의 기존 네 빈 항목을 유지한다.
- 참고: [web-push API](https://github.com/web-push-libs/web-push#api-reference), [Supabase pg_cron·pg_net·Vault 예시](https://supabase.com/docs/guides/functions/schedule-functions).

### 사용자 적용 순서와 수신 확인

1. Supabase에서 `pg_cron`·`pg_net`을 활성화하고 Vault `cron_secret`·`app_url`을 등록한다. 시크릿 값은 저장소에 넣지 않는다.
2. 새 마이그레이션을 원격에 적용하고 Vercel 환경 변수 네 개를 설정한 뒤 배포한다. 공개 VAPID 키 변경 시 재빌드와 재구독이 필요하다.
3. 설치한 iPhone PWA와 다른 브라우저에서 웹 푸시를 켠다. 권한 거부·홈 화면 미설치 안내, 해지, 다른 구성원의 공유 일정 추가·수정·삭제를 확인한다.
4. SCN-CAL-5~6·SCN-ACC-5: 시작 전·사용자 시각 아침 요약·빈 날·개인 일정·분 내 중복 호출과 알림 클릭 이동을 확인한다. 시크릿 없는 호출은 401이어야 한다.

로컬 단위 검사는 원격 DB의 RLS·트랜잭션 실행과 실제 iOS 수신을 대신하지 않는다.

### 워커 시크릿 운영 (r114-f6)

- `CRON_SECRET`과 Vault `cron_secret`에는 암호학적으로 안전한 생성기의 **최소 32바이트 무작위값**을 인코딩해 같은 값으로 등록한다. 사람이 만든 비밀번호를 쓰지 않는다.
- `notification_worker`는 anon 호출이 가능하고 DB 내부 비교는 상수 시간 비교가 아니다. 시크릿 유출 시 모든 가정의 워커 데이터에 접근할 수 있으므로 서버·Vault에만 보관하며 로그·이슈·브라우저에 노출하지 않는다.
- 교체 시 `kimjipsa-notifications` cron을 잠시 비활성화하고 진행 중인 호출이 끝난 뒤 Vault `cron_secret`을 새 값으로 갱신한다. 배포 환경 `CRON_SECRET`도 같은 값으로 교체해 재배포하고, 인증된 호출 성공·이전 값의 거부를 확인한 뒤 cron을 다시 활성화한다. 5분 내 끝내면 보충 창에서 누락을 회복할 수 있다.
- 웹 푸시 on/off는 계정 전체에 적용하며 각 기기의 구독은 유지한다. 구독이 없는 기기는 설정의 ‘이 기기에서 받기’로 연결한다. 로그아웃은 해당 기기 구독의 서버 삭제와 브라우저 해지를 시도한다. 서버 삭제가 실패해도 기기 해지를 시도하고, 어느 단계에서 오류가 나도 로그아웃은 계속 진행한다.
- 구독 자동 교체 시 새 구독을 해지하고 만료 endpoint 정리를 시도한다. 다른 로그인 사용자의 구독으로 자동 연결하지 않으며, 설정에서 다시 연결한다. iOS 실제 기기의 클릭 이동·구독 만료 확인은 별도로 필요하다.

### 로컬 SQL 통합 테스트

`src/entities/notification/api/worker.database.test.ts`는 `KIMJIPSA_TEST_DATABASE_URL`이 있을 때만 실행한다. `psql`과 P5b까지 적용한 폐기 가능한 로컬 Supabase DB가 필요하며 localhost 주소만 허용한다. 두 DB 연결로 같은 예약을 경쟁 실행하고 알림·로그 각 1건, 시작 시각 변경 후 새 알림, 다른 사용자의 endpoint upsert 거부를 확인한다. 테스트 fixture는 정리하며 실제 푸시는 발송하지 않는다. 환경 변수가 없으면 건너뛰므로 일반 단위 검사 통과가 SQL 검증 통과를 뜻하지 않는다.

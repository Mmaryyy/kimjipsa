# 0024. 가정 공유 데이터 변경 신호(Realtime broadcast)

- 결정 ID: ADR-0024 (관련 DEC: DEC-015)
- 결정 날짜: 2026-11-24
- 상태: CONFIRMED (2026-11-24 사용자 승인. 2026-11-23 초안, 2026-11-24 Codex 리뷰 r316 반영 개정)

## 배경

가정 구성원 여럿이 일정·카테고리·재고·장바구니·할 일·프로젝트를 함께 고친다. 지금은 화면마다 동기화 방식이 다르다(2026-11-24 코드 기준).

| 데이터 | 실시간 | 주기 조회 |
| --- | --- | --- |
| 집사 대화 | 비공개 broadcast `family:<id>:chat`, 내용 없이 `{"changed":true}` → 다시 조회(events·inventory·cart도 무효화) | 60초, 가입 직후·마운트·복귀 때도 조회 |
| 장바구니 | `postgres_changes`(cart_items·frequent_cart_overrides·inventory_categories·units) | 연결 중 30초, 소켓 미연결·목업 1초, 오프라인·mutation 중 정지 |
| 할 일 | `postgres_changes`(todo_changes INSERT/UPDATE) | 30초 |
| 일정 | `postgres_changes`(events, 시간만 담은 테이블, ADR-0012) | 목록·상세 30초(카테고리 훅은 없음) |
| 프로젝트 | `postgres_changes`(8개 테이블) | 목업 밖 30초 |
| 재고 | 없음 | 본문 30초(변경 중 정지), 재고 메타 30초 |
| 알림 | 없음 | 60초 |

문제:

- 실시간이 있는 화면도 30초 폴링을 함께 돌려, 바뀐 것이 없어도 열린 화면마다 계속 서버를 부른다.
- 재고는 실시간이 없어 배우자의 변경이 최대 30초 늦게 보인다.
- `postgres_changes`는 바뀐 행을 그대로 보낸다. 개인 일정처럼 일부 열을 숨겨야 하는 데이터는 테이블을 나눠야 했다(ADR-0012). 새 공유 데이터를 붙일 때마다 같은 검토가 필요하다.

## 검토한 대안

- **A. DB 트리거 → Supabase Realtime 비공개 broadcast로 "바뀐 주제"만 전파 (제안)**: 집사 대화가 쓰는 채널·권한 정책(`realtime.messages` RLS)을 넓힌다. 새 기반 시설이 없다.
- **A'. 가정별 변경 표시 행 하나를 `postgres_changes`로 구독**: 지금 `todo_changes`가 쓰는 방식. 행 내용 대신 신호만 나가지만, 변경마다 행을 계속 쓰고 가정별로 같은 행을 두고 경합한다. 수신 범위·복구 설계는 A와 똑같이 필요하다.
- **B. 별도 웹소켓 서버**: 서버 운영, 인증·가정 권한 검사를 새로 만들어야 한다. Vercel 함수는 오래 붙잡는 연결 용도가 아니다.
- **C. 맥미니 워커가 이벤트 중계**: 집 네트워크·맥미니가 멈추면 모든 구성원의 동기화가 멈춘다. 집사는 멈춰도 되지만 장바구니 공유는 멈추면 안 된다.
- **D. 모든 공유 테이블에 `postgres_changes`**: 행 내용이 그대로 가므로 테이블마다 개인정보 검토가 필요하고, 구독자마다 RLS 평가 비용이 든다.

## 제안하는 결정 (A)

### 채널과 수신 범위

- **가정 채널** `family:<family_id>:changes`: 그 가정 구성원 모두가 봐도 되는 변경만 보낸다.
- **사용자 채널** `user:<user_id>:changes`: 본인만 봐야 하는 변경(개인 할 일, 개인 일정 상세, 알림)을 본인의 다른 기기·탭에 보낸다.
- 수신 정책(`realtime.messages` SELECT)은 기존 집사 대화 정책처럼 **토픽 문자열 전체를 일치**시킨다. 가정 채널은 `'family:' || private.current_family_id() || ':changes'`, 사용자 채널은 `'user:' || auth.uid() || ':changes'`. 브라우저에는 송신(INSERT) 권한을 주지 않는다.

### 신호 내용

```json
{ "topic": "inventory" }
```

- 데이터 행도, 바꾼 사람(actor)도, 탭 id(origin)도 넣지 않는다. 받은 쪽은 topic의 쿼리를 다시 조회하고, 조회는 서버 라우트에서 요청자 권한으로 걸러진다.
- actor·origin을 빼는 이유: 가정 신호에 actor·origin이 있으면 배우자가 "누가, 어느 탭에서, 언제" 바꿨는지를 개인 일정·할 일 활동과 연결할 수 있다(r316-f2). 지금 화면에 actor가 꼭 필요한 곳은 없다. 필요해지면 그 화면의 조회 응답에 담는다.
- `topic`(초안): `events`, `event-categories`, `inventory`, `inventory-meta`(inventory_categories·units·locations), `cart`(cart_items·frequent_cart_overrides), `todos`, `projects`(project_* 전체), `family`(memberships·families), `notifications`(사용자 채널만).

### 개인 데이터의 발행 규칙

- **할 일**: 공유 상태에 영향이 있는 변경(변경 전 또는 후가 공유)만 가정 채널로 보낸다. 지금 `todo_changes` 규칙과 같다. 개인 할 일 변경은 작성자의 사용자 채널로만 보낸다. 개인 할 일의 존재와 생성·완료 시각이 배우자에게 새로 드러나지 않는다(r316-f1, CAL-18).
- **일정**: 배우자가 보는 것(시간 칸·공개 상태)이 실제로 바뀔 때만 가정 채널로 보낸다. 개인 일정의 제목·장소·메모만 바뀌면 작성자의 사용자 채널로만 보낸다(r316-f2, ADR-0012). 지금 일반 저장 RPC는 내용만 바꿔도 `events`를 UPDATE하므로, 시간 칸 신호는 "시간·공개 상태 열이 바뀌었는지"로 판단한다(`UPDATE OF` 열 지정 또는 OLD/NEW 비교).
- **알림**: 받는 사람의 사용자 채널로만 보낸다. 가정에서 빠진 사람에게는 보내지 않는다(현재 가정 조건은 알림 조회 정책과 같게).
- **D-day 숨김**(dday-dismissals)은 개인 설정이라 가정 채널에 넣지 않는다. 같은 사용자의 기기 간 동기화가 필요하면 사용자 채널로 보낸다.

### 발행 방식 (DB)

- 공유 테이블마다 `AFTER INSERT`·`AFTER UPDATE`·`AFTER DELETE` **statement 트리거**를 따로 선언하고, transition table(`NEW TABLE`·`OLD TABLE`)에서 신호를 받을 대상(가정·사용자)을 `DISTINCT`로 구한다. 대상이 없으면 보내지 않는다. UPDATE로 가정·받는 사람이 바뀌면 이전과 이후 대상 모두에 보낸다. "지금 요청한 사용자의 가정"을 대상으로 쓰지 않는다(r316-f7).
- 테이블마다 대상 열이 다르다: events·event_details·event_exceptions·project_* 는 `family_id`, families는 `id`, notifications는 `user_id`.
- 부모 삭제로 상세가 연쇄 삭제될 때는 자식 트리거에서 부모 공개 상태를 다시 조회할 수 없다. 삭제 신호는 부모 테이블의 OLD 행 또는 해당 RPC에서 정한다.
- **대량 변경 RPC**(예: 장바구니 재입고, 최대 500건을 항목마다 따로 INSERT/UPDATE)는 문장마다 신호가 나가 최대 1,000개가 될 수 있다. 브라우저 쪽 묶기는 DB 발행량을 줄이지 못한다. 이런 RPC는 성공 시 트랜잭션 안에서 대상·topic마다 한 번만 보내고, 그동안 일반 트리거는 같은 트랜잭션에서 다시 보내지 않는다(트랜잭션 로컬 설정으로 억제). Free 한도는 월 200만 메시지와 **초당 100메시지**이고 받는 탭마다 집계된다(r316-f8).

### 클라이언트

- 공용 구독 훅이 가정 채널과 사용자 채널을 구독하고, 받은 topic을 TanStack Query 키 목록으로 바꿔 `invalidateQueries`한다. 보고 있는 화면(활성 쿼리)만 다시 조회된다.
- topic→쿼리 키 표를 RT2 전에 정한다. 교차 의존이 있다: 장바구니 응답은 멤버·단위·카테고리도 읽고, 카테고리·단위 변경은 cart와 inventory-meta를 함께 무효화한다. 일정은 events(범위·상세), event-categories, 저장 색 목록, dday-dismissals 키가 따로 있다(r316-f9).
- 내 mutation이 진행 중인 키에 신호가 오면 "다시 조회 필요" 표시만 남기고, 마지막 mutation이 성공하든 실패하든 끝난 뒤 한 번 조회한다. 신호가 계속 와도 미루는 시간에 상한(3초, d284)을 둔다.
- 같은 topic 신호가 몰리면 짧은 시간(예: 300ms) 안에서 한 번으로 묶는다. 이것은 HTTP 재조회만 줄인다.
- 집사 대화 채널도 events·inventory·cart를 무효화하므로, 두 채널이 같은 변경에 대해 두 번 조회하지 않는지 RT2에서 확인한다.

### 내 변경 걸러내기 (origin): 처음엔 넣지 않는다

- 사용자 결정(2026-11-24, d283): 처음에는 받은 신호를 모두 처리한다. 내가 바꾼 것도 한 번 더 조회한다.
- 중복 조회가 측정돼 문제가 되면 그때 추가한다. 추가할 때 조건:
  - 탭 id는 sessionStorage가 아닌 **문서 인스턴스별 메모리 UUID**로 만든다. sessionStorage는 opener가 있는 새 탭에 복제돼 두 탭이 서로의 신호를 버릴 수 있다(r316-f6).
  - 버리는 조건은 "origin이 같고, 그 쿼리의 내 mutation이 성공해 캐시를 갱신했을 때"뿐이다. 응답이 유실돼 롤백된 경우는 버리지 않는다.
  - origin은 사용자 채널 신호에만 싣는다(가정 채널에 싣지 않는다, 위 "신호 내용").
  - 전달 경로(r316-f5): 요청별 Supabase 클라이언트의 `global.headers`로 보내면 RPC·`security definer` 함수·같은 트랜잭션의 트리거에서 `current_setting('request.headers', true)`로 읽힌다. 빈 문자열은 NULL로, UUID가 아니면 null로 처리한다. 헤더는 인증·가정 판정에 쓰지 않는다. 워커·cron(`net.http_post`)·직접 SQL 예약 작업은 탭 헤더가 없어 origin이 null이다. 브라우저가 집사 제안을 [확인]하면 그 요청의 origin이 내부 RPC까지 전달된다.

### 복구와 최신성

신호는 유실될 수 있으므로(구독 거부, 소켓 끊김, `SUBSCRIBED` 직후 조회 실패) 신호만으로 최신성을 보장하지 않는다(r316-f4).

- 처음 가입 직후, 앱 복귀(visibility/focus), 네트워크 재연결, 채널 재구독 때 같은 복구 경로로 활성 쿼리를 한 번 다시 조회한다. 세션이 만료됐을 때 QueryProvider가 조회를 막는 동작은 유지한다.
- 채널이 연결되지 않은 동안(실패·재연결 중)은 활성 쿼리의 폴링을 유지한다(장바구니의 지금 방식과 같다).
- 연결이 정상이어도 유실을 메우도록 **저빈도 확인 조회**를 남긴다(5분, d284).
- Broadcast Replay(최대 25건, 선택 기능)는 복구의 전제로 쓰지 않는다.

### 권한 회수

- Realtime은 소켓의 RLS 판정을 JWT가 갱신·만료될 때까지 캐시한다. 가정에서 빠진 사람도 그때까지 신호를 받을 수 있다. 이 프로젝트의 JWT 만료는 기본값 **1시간**이다(`supabase/config.toml`에 별도 설정 없음).
- 신호에는 topic만 있으므로 그 1시간 동안 새는 정보는 "가정 데이터 중 어느 종류가 언제 바뀌었는지"뿐이고, 다시 조회는 서버 권한 검사에서 막힌다.
- 로그아웃·가정 탈퇴·세션 갱신 때 클라이언트가 채널과 대기 중인 조회를 정리한다.
- 즉시 차단이 필요해지면 서버에서 강제 연결 해제할 수 있는 구조를 따로 검토한다(이번 범위 아님).

### 목업

- 첫 단계는 지금의 목업 조회 방식(장바구니 1초 폴링 등)을 그대로 둔다. 목업은 쿠키로 찾은 서버 메모리 세션을 공유하므로 탭 사이 변경은 폴링이 감지한다(r316-f10).
- 나중에 목업에서도 폴링을 없애면 같은 세션의 여러 탭에 신호를 전달하는 방법과, 계정·세션 전환 때 구독 정리를 함께 정한다.

## 단계 (RT1~RT3)

복구와 호환성을 origin보다 먼저 검증한다(r316-f11).

- **RT1 재고 시범**: 가정 채널·수신 정책·재고 트리거만 붙인다. 신호에는 topic만 싣고 **기존 폴링은 유지**한다. 일반 쓰기, 집사 확인 경로, 다른 가정 차단(배우자 세션으로 다른 가정 채널 구독 거부)을 확인한다.
- **RT2 공용 구독·복구**: 공용 구독 훅, 사용자 채널, topic→쿼리 키 표, mutation 중 신호 처리, 연결 복구 경로를 넣는다. 일정·카테고리·할 일에 적용하고 개인 데이터 발행 규칙을 DB 테스트로 확인한다. 전경 유실·재가입·mutation 중 신호·목업을 확인한 뒤 범위를 넓힌다.
- **RT3 전환과 정리**: 장바구니·프로젝트·알림을 옮기고, 도메인별로 기존 폴링을 저빈도 확인 조회로 줄이고 `postgres_changes`를 제거한다. 배포 중 이전 클라이언트가 살아 있는 동안에는 기존 신호(todo_changes 등)를 계속 발행하고, 다음 배포에서 제거한다.
- **origin**: 중복 조회가 측정될 때 별도 작업으로 진행한다.

## 결정 이유

- 이미 운영 중인 패턴(집사 대화)을 넓히는 것이라 새 서버·의존성이 없다.
- 신호에 데이터·actor·origin이 없고, 개인 데이터는 사용자 채널로만 가므로 배우자에게 새로 드러나는 정보가 없다.
- 바뀐 것이 있을 때, 보고 있는 화면만 조회한다. 폴링은 끊김 중과 저빈도 확인으로만 남는다. Supabase 무료 한도(동시 연결 200, 월 메시지 200만, 초당 100) 안에서 가정 단위 사용은 충분하다. 대량 RPC는 트랜잭션당 한 번 발행으로 초당 한도를 지킨다.

## 예상 영향

- DB: 공유 테이블의 statement 트리거, 발행 함수, 가정·사용자 채널 수신 정책, 대량 RPC의 한 번 발행(마이그레이션, 원격 적용은 사람이 한다).
- 클라이언트: 공용 구독 훅, topic→쿼리 키 표, 화면별 폴링 축소·`postgres_changes` 제거. 목업은 첫 단계에서 그대로.
- 서버: origin을 넣기 전까지는 바뀌지 않는다.

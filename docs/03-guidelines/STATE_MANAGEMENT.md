# 상태 관리

상태: 상태 종류별 기준은 **PROPOSED**이다. 라이브러리(TanStack Query, 폼 라이브러리, 전역 스토어)는 `TECH_STACK.md`와 DEC-006이 승인된 뒤 반영하고, 그 전에는 라이브러리를 전제로 한 강제 규칙을 만들지 않는다. 기존 합의: 상태는 가능하면 저장하지 말고 현재 값에서 계산한다 (`CODING_STANDARDS.md` §5).

## 1. 상태 종류별 기준

| 종류 | 둘 곳 | 이 프로젝트의 예 |
| --- | --- | --- |
| Local State | 컴포넌트 안(`useState`, `useReducer`) | 다이얼로그 열림, 입력 중인 검색어, 체크 중인 행 선택 |
| Global Client State | entity/widget `model/`에 필요할 때만 작은 스토어 | 챗봇 창 열림/최소화(최소화 여부는 서버에도 사용자별로 기억 BOT-01), 마지막 읽기 전용 상태 표시 |
| Server State | 서버 상태 라이브러리 캐시(제안) + Supabase Realtime | 일정, 재고, 장바구니, 대화, 설정, 멤버 |
| URL State | 쿼리 문자열·경로 | 달력 뷰(월/주/일)와 기준 날짜, 재고 필터(보관 장소·카테고리), 검색어 |
| Form State | 폼 라이브러리(제안) 또는 로컬 state | 일정 등록 폼, 품목 폼, 재고 반영 확인 화면, 설정 폼 |

## 2. 판단 규칙

1. **서버에서 온 데이터는 Server State다.** 전역 스토어에 복사하지 않는다. 실시간 변경은 이벤트로 캐시를 갱신한다.
2. **파생 가능한 값은 상태로 두지 않는다.** 부족/없음/임박(INV-03, INV-05), D-day 남은 일수, N주년(CAL-16), "수정됨" 여부는 기준값과 현재값에서 계산한다.
3. **새로고침해도 유지돼야 하거나 공유할 URL이면 URL State.** 서버 데이터를 불러오는 URL 쿼리는 URL이 원천이고, 화면 1부터/API 0부터 같은 변환은 한 훅에 모은다.
4. **한 컴포넌트와 그 자식만 쓰면 Local State.** 두 곳 이상이 쓰게 될 때 올린다.
5. **전역 스토어는 서버 상태도 URL도 아닌 UI 상태에만 쓴다.** 모든 API 호출을 스토어에 통과시키는 구조는 쓰지 않는다 (`TECH_STACK.md` REJECTED).
6. 사용자별로 영속돼야 하는 UI 설정(홈 뷰, 위젯 개수, 푸시 on/off, 챗봇 최소화)은 서버 설정으로 저장하고 Server State로 읽는다 (ACC-11, ACC-12, BOT-01).

## 3. 영역별 메모

| 영역 | 메모 |
| --- | --- |
| 일정 | 개인 일정 마스킹은 서버가 한다. 클라이언트 상태에 숨긴 값이 들어오지 않는다. 공유 일정 변경은 상대 화면에 반영돼야 하므로 실시간 방식은 DEC-001과 함께 정한다 |
| 재고 | +/- 조정은 낙관적 갱신 후보. 실패하면 되돌리고 오류를 안내한다 |
| 장바구니 | Realtime 구독으로 목록 갱신(CART-02). 체크는 낙관적 갱신 후보. 연결이 끊기면 마지막 목록을 읽기 전용으로 두고 복구 시 최신 목록으로 동기화한다(CART-14). 오프라인 편집은 지원하지 않으므로 쓰기 큐를 만들지 않는다 |
| 챗봇 | 대화 목록은 서버 상태, 스트리밍/전송 중 상태는 로컬. 확인 대기 액션은 서버 상태이며 5분 만료를 표시한다 |
| 구매 완료 | 재고 반영 확인 화면의 수정 값은 폼 상태. 닫으면 폐기하고 서버 데이터는 바뀌지 않는다 (SCN-CART-5) |

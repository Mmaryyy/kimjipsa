# 테스트 전략

상태: 원칙과 요구사항 연결 방식은 **PROPOSED**이다. 도구는 Vitest + Testing Library(단위·컴포넌트), Playwright(E2E)로 **CONFIRMED**다(ADR-0006). CI 구성은 별도 승인이다. **테스트·빌드 같은 검증 실행은 사용자 승인 뒤에만 한다** (`AGENTS.md`). 이 문서는 무엇을 어떻게 테스트할지 정하는 것이지, 자동으로 돌리라는 뜻이 아니다.

## 1. 요구사항 연결

- 테스트 이름이나 `describe`에 요구사항 ID와 시나리오 ID를 넣는다. 예: `describe("CAL-04 개인 일정 가림", ...)`, `it("SCN-CAL-2 …")`.
- 명세의 확인 시나리오(`SCN-<영역>-<번호>`)는 E2E 또는 통합 테스트의 기본 입력이다.
- 새 요구사항을 구현하면 최소 하나의 테스트가 그 ID를 가리키게 한다. ID로 `rg` 하면 구현·테스트가 함께 찾아지도록 한다.

## 2. 테스트 종류와 대상

| 종류 | 대상 | 예 |
| --- | --- | --- |
| 단위 | 순수 함수·규칙(entity `lib`) | 부족/없음 판정(INV-03), 임박(INV-05), D-day 계산과 연도 넘김(CAL-06, SCN-CAL-9), N주년(CAL-16), 개인 일정 필터(CAL-04), 자주 사는 품목 계산(CART-05), 초대 만료·1회 사용(ACC-05), 확인 대기 5분 만료(BOT-08) |
| 컴포넌트 | 상태별 UI | 재고 배지, 확인 대화상자(제목 표시·취소 시 불변), 빈/로딩/오류 상태, 말풍선의 동작 줄이기 |
| 통합(서버 라우트·DB) | 권한 필터, 챗봇 도구, 구매 → 재고 반영 | 배우자 요청 시 개인 일정 마스킹, 직접 요청 즉시 실행 vs 자체 판단 pending, 만료 후 확인 거절, 단위 삭제 차단(SCN-INV-4), 탈퇴 시 삭제 범위 |
| E2E | 두 사용자 흐름 | 실시간 공동 편집(SCN-CART-1), 개인 전환 후 배우자 화면(SCN-CAL-2), 온보딩·합류(SCN-ACC-1, 2), 장보기 루프 |

## 3. 우선 검증 대상

개인정보·돈·되돌리기 어려운 동작을 먼저 본다.

1. **프라이버시(최우선)**: 배우자의 브라우저·API 응답·Realtime 페이로드·챗봇 응답에 개인 일정의 제목·장소·메모가 없음 (CAL-04, BOT-10, SCN-CAL-2, 4). 화면 가림만 검사하지 말고 응답 데이터를 직접 검사한다.
2. 변경 경로 구분: 직접 요청은 확인 없이, 자체 판단은 확인 후에만 (BOT-07, BOT-08, SCN-BOT-5~7).
3. 데이터 정합: 구매 반영 병합/신규, 닫으면 불변 (INV-12, CART-07~09, SCN-INV-6, SCN-CART-4, 5).
4. 키 보안: 키가 응답·로그·클라이언트 번들에 없음, 끝자리만 노출 (ACC-08).
5. 가정 격리: 다른 가정의 데이터 접근 불가 (RLS 정책 테스트).

## 4. 예외 상황 검증

- AI 키 없음/오류/한도 초과 (BOT-05, BOT-16, SCN-BOT-3)
- 초대 링크 사용됨/만료/이미 가정 소속 (SCN-ACC-2, 3)
- 연결 끊김 시 장바구니 읽기 전용과 복구 시 동기화 (CART-14)
- 동시 편집 충돌, 중복 항목 안내 (CART-12, INV-16)
- 시간대 경계: 자정 전후 D-day, 종일·기간 일정
- 제공자별(Claude, Gemini) 챗봇 핵심 시나리오·OCR 점검표 (기획서 §12, 통과 기준은 점검표를 만들 때 정함)

## 5. 원칙

- 기능 요구가 아닌 구현 세부(내부 상태, CSS 클래스)를 단정하지 않는다. 접근성 역할·텍스트로 찾는다.
- 외부 서비스(AI, 구글, 푸시)는 테스트에서 어댑터 경계에서 대체한다. 실제 키로 호출하지 않는다.
- 테스트 데이터에 실제 개인정보를 쓰지 않는다.
- 실행 규칙: 테스트 실행은 사용자 승인 후. 저장소 전체에 기존 실패가 있으면 변경 파일 결과와 구분해 보고한다.

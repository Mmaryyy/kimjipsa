# 코딩 표준

코드를 새로 쓰거나 고칠 때 읽는다. 기획·문서 작업에는 필요 없다.

이전 프로젝트(`casting_monster_frontend`의 `model`, `unas-react`)에서 쓰던 규칙 중 이 프로젝트(Next.js, Supabase, Vercel, PWA)에 맞는 것만 옮겼다. 폴더 경로와 도구 이름은 프로젝트 초기 세팅 때 확정하고, 달라지면 이 문서를 같이 고친다.

## 1. 구조와 책임

- 폴더 구조는 FSD를 따른다. 레이어, 슬라이스, import 방향, Next.js 연결은 `docs/02-architecture/FSD.md`를 기준으로 한다. 파일을 새로 만들거나 옮길 때 그 문서를 읽는다.
- 슬라이스 안의 데이터 흐름은 `api → model → ui`다. 컴포넌트가 Supabase 클라이언트나 `fetch`를 직접 다루지 않고 `model`의 훅을 거친다. `api/`는 `api.ts`(호출), `type.ts`(요청·응답 타입)로 나눈다.
- 슬라이스 밖에서는 항상 `index.ts`(public API)로 import한다.
- `node:*`를 쓰는 서버 전용 모듈은 클라이언트가 쓰는 코드와 같은 배럴(`index.ts`)에서 내보내지 않는다.
- 슬라이스 안에서도 폴더는 기술 종류보다 개념과 책임으로 나눈다. 복합 UI는 `compare/`, `result/`, `common/`처럼 읽히게 묶는다.
- 긴 컴포넌트에서 독립된 섹션, 반복되는 행, 자체 입력 로직이 있는 부분은 분리한다. JSX 한두 줄까지 형식적으로 쪼개지는 않는다.
- 범용 컴포넌트는 쓰는 쪽 도메인을 알지 않는다. 화면마다 다른 조건은 `if`가 아니라 범용 prop(`size`, `appearance`, `tone`, slot)으로 받는다.
- API 호출이 던지지 않고 `{ ok: true, data } | { ok: false, error }` 결과를 돌려주게 하면, 컴포넌트에서 `try/catch`를 반복하지 않고 `result.ok`로 분기할 수 있다. 이 방식을 쓰기로 하면 공용 함수 하나로 감싼다.

## 2. 컴포넌트 재사용

- 새 UI를 만들기 전에 `shared/ui`, `entities/*/ui`, `widgets`, `features/*/ui`에서 `rg`로 같은 역할의 구현이 이미 있는지 먼저 찾는다.
- 있으면 그것을 쓴다. 표현이 모자라면 소비 화면에서 비슷한 코드를 만들지 말고 원본에 범용 prop이나 CVA variant를 추가한다. 추가한 variant의 기본값은 기존 화면의 외형과 동작을 그대로 두게 한다.
- 두 군데 이상에서 같은 모양(폼 필드, 오류 배지, 목록 행, 상태 배지, 확인 대화상자, 섹션 제목, 삭제 버튼)이 필요하면 복사하지 않고 공용 컴포넌트로 만든다. 도메인을 모르는 공용은 `shared/ui`, 도메인 표현(상태 배지, 카드)은 해당 entity의 `ui/`, 한 기능에서만 쓰는 것은 그 slice의 `ui/` 안에 둔다. 두 페이지 이상이 쓰는 조합 블록은 widget으로 올린다.
- 비슷한 컴포넌트가 이미 여러 개면 하나 더 만들지 말고 공용으로 합친 뒤 쓴다. 합칠 때 기존 동작과 접근성 역할·텍스트(테스트가 의존하는 값)를 바꾸지 않는다.
- 공용 `Button`이 있으면 `<button>`에 `className`을 붙여 같은 역할을 다시 만들지 않는다. 필요한 모양이 없으면 `Button`에 variant를 추가한다.
- shadcn을 쓰는 경우, 공용 구현이 없더라도 shadcn이 해당 primitive를 제공하는지 먼저 확인하고 `components.json` 설정에 맞춰 추가한다. 더 낮은 수준의 primitive를 직접 조립하지 않는다.
- 기존 구현을 쓰지 못하는 기술적 이유가 있을 때만 별도 구현하고, 그 이유를 완료 보고에 적는다.
- 작업을 마칠 때 새로 복사한 JSX/로직 덩어리가 없는지 스스로 점검하고, 있었다면 보고에 적는다.
- 슬라이스 밖에서는 `index.ts`로만 import한다. 깊은 경로 import는 금지이고, 무거운 서드파티를 `index.ts`에 재export하지 않는다. 다이얼로그를 여는 함수와 다이얼로그 슬라이스 사이에 순환을 만들지 않는다.

## 3. 네이밍

- 컴포넌트, 파일, 타입, 변수는 하나의 용어로 통일한다. UI가 `SourceBadge`면 타입과 변환 함수도 `SourceBadgeData`, `toSourceBadgeData`로 맞추고 `SourceTag`를 섞지 않는다.
- 이름은 약어 대신 뜻이 드러나게 짓는다. 현재 역할과 다른 과거 이름을 호환 명목으로 남기지 않는다.
- `data`, `item`, `value`는 작은 지역 범위에서만 쓴다. 경계를 넘는 값에는 `candidate`, `sourceBadge`처럼 역할을 드러낸다.
- React 예약 prop인 `key`를 일반 prop 이름으로 쓰지 않는다. `fieldKey`처럼 쓴다.
- 파일 역할 접미사를 정확히 쓴다: 데이터는 `*.constants.ts`, CVA 선언은 `*.variants.ts`, 순수 함수는 `*.utils.ts`.
- 훅은 `useXxx`로 짓고, 컴포넌트에 내보내는 핸들러는 `onXxx`로 이름 붙여 `useCallback`으로 감싼다.
- 컴포넌트 이름과 시맨틱 HTML 규칙은 `COMPONENT_NAMING.md`를 따른다(사용자 결정, 2026-10-15). 처음 보는 사람도 목적과 쓰임을 짐작할 수 있는 범용 이름을 쓰고(`BottomNavigation`, `PageHeader`), `LargeTitle` 같은 디자인 용어나 `controls.tsx` 같은 묶음 파일명은 쓰지 않는다. 파일 이름은 안에 든 컴포넌트 이름을 따른다.

## 4. 타입과 단일 원천

- 도메인 키, 라벨, 옵션은 한 곳에서 `as const`로 정의하고 나머지는 거기서 파생한다. 예를 들어 재고 상태(`enough`, `low`, `none`)와 일정 공개 범위(`shared`, `private`)의 값, 화면 라벨, 색, union 타입을 따로 유지하지 않는다.
- 상수와 매핑의 누락은 `satisfies Record<DomainType, ...>`로 컴파일 때 검증한다.
- 래핑하는 컴포넌트의 props는 손으로 다시 적지 말고 `ComponentProps<typeof Component>`에서 가져온다.
- 타입만 쓰는 import는 `import type`을 쓴다.
- 라우트 경로와 라벨도 상수 한 곳에서 정의하고, 링크와 이동은 그 상수를 쓴다.
- `false`, `0`, 빈 문자열, `null`, `undefined`를 같은 빈 값으로 취급하지 않는다. 수량 `0`은 유효한 값이므로 `!value`로 빈 값을 판정하지 않는다.
- 목록 응답이 상세 필드를 포함한다고 가정하지 않는다. 표시 로직은 타입만 보지 말고 실제 응답에 필요한 필드가 있는지 확인한다.
- `any`와 `as any`로 타입 오류를 넘기지 않는다. 응답 타입을 정의해서 쓴다.

## 5. 상태와 파생 값

- 상태는 가능하면 저장하지 말고 현재 값에서 계산한다. 재고의 부족·없음(INV-03), D-day 남은 일수, 유통기한 임박 여부는 저장하지 않고 계산한다.
- 파생 가능한 UI 상태를 별도 `Set`이나 boolean으로 누적하지 않는다. "수정됨" 같은 상태는 이벤트 이력이 아니라 기준값과 현재값의 비교로 구한다.
- 같은 필드의 동일성 규칙(대소문자, 공백, 순서 무시 여부)은 한 곳에서 관리한다.
- 서버 데이터를 불러오는 URL 쿼리(페이지, 필터)는 URL을 상태의 원천으로 삼고, 화면은 1부터, API는 0부터 쓰는 경우 변환을 한 훅에 모은다.

## 6. 스타일

Tailwind + CVA + shadcn/ui 기준이다(ADR-0004).

- `size`, `selected`, `disabled`, `pressed`, 의미별 색(`tone`)처럼 시각적 variant는 `class-variance-authority`로 선언하고 `*.variants.ts`에 둔다. 라벨, 옵션 같은 데이터는 `*.constants.ts`에 두고 둘을 한 파일에 섞지 않는다. variant 이름 목록은 데이터가 아니다. CVA 선언이 단일 원천이므로 타입은 `VariantProps`로 뽑고, 같은 키를 `*.constants.ts`에 다시 적지 않는다. 화면이 variant를 순회해야 하면 `Record<Variant, ...>`처럼 키 누락을 컴파일러가 잡는 형태로 그 화면 쪽에 둔다.
- JSX 안에서 variant 스타일을 긴 삼항이나 조건부 클래스 조합으로 반복하지 않는다.
- CVA는 외형을 정하고, 문구와 행동은 props나 도메인 매핑이 정한다.
- `kj-*` CSS는 `components` 레이어에 두고, 호출부에서 Tailwind 유틸리티로 덮어쓴다.
- 클래스 합치기는 `cn()`(`clsx` + `tailwind-merge`)을 쓴다.
- 색·간격은 디자인 토큰 파일의 토큰만 쓰고, TSX나 별도 CSS에 값을 중복 정의하지 않는다. 토큰 원본은 `docs/design/tokens.css`이고, 앱 안의 토큰 파일은 `src/app/styles/tokens.css`이며, Tailwind 테마는 `src/app/styles/globals.css`에서 CSS 변수를 참조한다.
- 아이콘(svg)의 색은 불투명 토큰(`--icon-*`)을 쓴다. 반투명 색은 선이 겹치는 곳이 진해져 얼룩져 보인다.
- 상태 색은 `variant`(`success · info · warning · error`), 글자 스타일은 타이포 `variant`(`docs/design/HANDOFF.md` §3)로 고른다.

## 7. UI 작성

- 모바일 우선으로 만들고, 실제 데이터 개수와 콘텐츠 길이에서 확인한다. 1개와 여러 개, 긴 이름, 이미지 없음, 빈 목록을 모두 본다.
- 여러 항목이 가능한 UI는 처음부터 목록이나 grid로 설계한다. 단일 샘플만 보고 전체 폭으로 고정하지 않는다.
- 빈 값 문구와 오류 문구는 기능 안에서 일관되게 쓰고, 한국어로 쓴다. 조사 결합이 어색해지는 동적 문장은 피한다.
- 아이콘만으로 뜻이 불분명한 핵심 행동에는 텍스트 라벨을 함께 둔다. 툴팁은 보조 설명으로만 쓴다.
- 로딩은 목록 모양의 skeleton, 빈 목록과 실패는 같은 빈 상태 컴포넌트(메시지, 아이콘, 행동)로 통일한다.
- 폼 오류는 해당 필드 근처에 인라인으로 보여 준다.

## 8. 코드 가독성

- 포매팅은 prettier가 맡는다. 설정은 `.prettierrc.json`이 원본이며(줄 너비 80자, 큰따옴표, 세미콜론, 후행 쉼표), 프로젝트 세팅 때 `format`, `format:check` 스크립트와 함께 추가한다. 손으로 맞추지 말고 `yarn format`을 쓴다.
- 코드 작업을 마치면 `yarn format`과 `yarn format:check`를 돌린다(실행 규칙은 `AGENTS.md`). 포매팅은 이번 작업에서 새로 쓰거나 고친 파일에만 적용하고, 상관없는 파일은 포매팅하지 않는다.
- 한 줄에 컴포넌트 전체나 긴 조건을 몰아 쓰지 않는다. 한 파일 한 줄짜리 코드는 포매터를 돌려도 읽기 어렵다.
- 포매터가 못 해 주는 부분은 직접 지킨다. 긴 삼항·`&&` 조건 렌더링·`map` 콜백은 변수나 파일 안의 헬퍼로 빼고, 삼항은 두 겹까지만 쓴다. 다른 파일에서 쓰는 컴포넌트로는 책임·재사용·상태 캡슐화가 있을 때만 나눈다(`COMPONENT_NAMING.md` §10).
- 설명이 필요한 줄에는 "왜"를 한 줄 주석으로 적는다. 코드가 이미 말해 주는 "무엇"은 적지 않는다. 훅과 변환 함수에는 규칙이 비자명할 때만 한 줄 문서 주석을 붙인다.
- 코드는 bottom-up으로 쓴다(사용자 결정, 2026-10-15). 구현 순서는 작은 단위(상수·타입·유틸·하위 컴포넌트)를 먼저 만들고, 그것을 조립해 큰 컴포넌트와 화면을 만든다. 파일 안에서도 쓰이는 것을 쓰는 것보다 위에 둔다. 내보내는 주 컴포넌트가 파일 맨 아래에 온다.
- 디버깅용 `console.log`는 남기지 않는다.

## 9. 커밋 메시지

이전 프로젝트의 이력을 따르되, 이 프로젝트는 앱이 하나라 앱 접두사는 쓰지 않는다.

- 형식은 `<type>: <설명>`이다. type은 `feat`, `fix`, `refactor`, `style`(보기만 바꾸는 변경), `design`, `docs`, `chore`, `wip`을 쓴다.
- 설명은 무엇을 했는지 한 줄로 쓴다. 영어와 한국어 모두 쓸 수 있고, 한 이력 안에서는 섞지 않는다.
- 요구사항 ID가 있으면 설명에 붙인다. 예: `feat: add shared event visibility toggle (CAL-03)`

## 10. 검증

- 정적 검증은 변경 파일 대상 ESLint와 전체 타입 체크 빌드다. 포매팅을 뺀 나머지 검증은 `AGENTS.md`의 작업 규칙에 따라 사용자 승인 뒤에 돌린다.
- 저장소 전체 lint에 기존 오류가 있으면 변경 파일의 결과와 구분해 보고한다.
- 새 순환 의존성 경고는 허용하지 않고 원인을 제거한다. 작업 범위 밖의 기존 경고는 새로 생긴 것인지 비교해서 정확히 보고한다.
- UI 변경은 가능하면 실제 브라우저에서 확인한다.
- 완료 보고에는 변경한 동작, 검증 결과, 남은 경고나 확인하지 못한 상태만 간결하게 적는다.

## 옮기지 않은 것

이전 프로젝트에서 이 프로젝트에 맞지 않거나 효용이 낮아 뺀 것이다. 필요해지면 그때 다시 검토한다.

- Zustand 스토어를 모든 API 호출의 필수 계층으로 두는 구조(`api → store → hook`). 이 프로젝트는 Supabase Realtime과 서버 라우트를 쓰므로 스토어는 필요할 때만 entity의 `model/`에 둔다.
- 종류별 최상위 폴더(`api/`, `stores/`, `hooks/`, `components/`, `pageComponents/`). FSD 레이어로 대체했다.
- `Box.Card.tsx` 같은 점 구분 파일명. 주변 파일의 현재 규칙을 따르는 것으로 충분하다.
- 제품용 컴포넌트 카탈로그(`BoxCard`, `PeopleCard`, `Table` 등)와 인물·모델 도메인 규칙(병합 화면, 프로필 이미지, 약관). 이 프로젝트에 없는 도메인이다.
- 디자인 시안 경로와 `HANDOFF.md` 운영 방식, 리팩터링 스킬(`rf`).
- 린트 설정(`exhaustive-deps`, `no-explicit-any`, `no-unused-vars`를 끈 것). 이 프로젝트는 기본값(켜짐)을 유지한다.
- 이전 코드에 있던 한 줄짜리 컴포넌트와 `as any` 사용. 따라 하지 않는다.
